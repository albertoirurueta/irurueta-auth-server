= Configuration

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

This page lists every configuration property the four applications implement: `auth-server`, `bff`,
`resource-server` and `service-client`. For each one it gives the environment variable that `application*.yml` maps
to it, the default when nothing is set, what it does and the profile where it matters.

A property can be set in several ways:

* in `application.yml` or a profile file (`application-<profile>.yml`) of the application's `boot` module;
* through the environment variable that the yml file maps with a placeholder such as
  `${AUTHSERVER_ISSUER_URL:http://localhost:9000}` (the value after the colon is the default);
* through any other environment variable, by Spring Boot's relaxed binding: upper case, dots and dashes replaced by
  underscores. For example `AUTHSERVER_MFA_MAX_FAILED_ATTEMPTS` sets `authserver.mfa.max-failed-attempts`, even
  though no yml file maps it;
* as a command-line argument, for example `--authserver.par.enabled=true`.

When a yml file sets a value, that value is the effective default, even if the code has another one. The tables say
so where the two differ. Most settings are bound into validated `@ConfigurationProperties` records: an invalid value
(a negative duration, an unknown provider, a malformed country code, ...) stops the application at startup with a
message that names the property.

In the tables, "none" means there is no default and "-" means no yml file maps an environment variable (relaxed
binding still works).

== Profiles

[cols="2,2,6",options="header"]
|===
|Profile
|Application
|What it switches

|`dev`
|`auth-server`
|Local development only. Starts the root `compose.yaml` with Spring Boot's Docker Compose support (PostgreSQL,
Mailpit), points mail at `localhost:1025`, sets the local redirect URIs of the seeded `bff` and `spa-public` clients,
seeds a demo user, the `bff` client with a generated secret and the public `device-client` (`DevDataInitializer`),
generates the key-encryption secret under `~/.irurueta-auth-server/` (`DevKeyEncryptionSecret`), generates a
self-signed server certificate for the X.509 TLS port when one is configured (`DevX509KeyStore`), keeps SMS messages
in memory and shows them at `/dev/sms-inbox`. Never activate it outside local development.

|`test`
|`auth-server`
|Activated by the integration tests (`@PostgresIT`). Selects the logging SMS sender, which keeps the messages in an
in-memory outbox. Not meant for a deployment.

|`twilio`
|`auth-server`
|Sends SMS through Twilio (`application-twilio.yml`). Ignored when `sns` is active too.

|`sns`
|`auth-server`
|Sends SMS through Amazon SNS (`application-sns.yml`). Credentials and region come from the AWS SDK default chains
(`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, the shared profile files or the instance role); no
project property is involved.

|`legacy-implicit`
|`auth-server`
|Enables the legacy implicit flow demo for the one client `legacy-implicit-spa` (`application-legacy-implicit.yml`).
Opt-in, outside OAuth 2.1, and never to be enabled in production. See xref:legacy-implicit.adoc[].

|`dev`
|`bff`
|Starts the root `compose.yaml` with Docker Compose and points the BFF at its own `bff` database
(`BffDevDatabase`).

|`opaque`
|`resource-server`
|Validates bearer tokens by introspection at the authorization server instead of as JWTs
(`application-opaque.yml`). See xref:resource-server.adoc[].

|`client-credentials`
|`service-client`
|Runs `ClientCredentialsCli`: gets a token with the client credentials grant and lists `GET /api/documents`. See
xref:client-credentials.adoc[].

|`device-flow`
|`service-client`
|Runs `DeviceFlowCli`: the device authorization grant against the framework endpoints. See xref:device-grant.adoc[].

|`token-exchange`
|`service-client`
|Runs `TokenExchangeCli`: exchanges the user's access token (`SERVICE_CLIENT_SUBJECT_TOKEN`) for one that names the
client as actor. See xref:client-credentials.adoc[].
|===

The SMS sender is chosen by profile, never by a property. The profile expressions are `twilio & !sns` (Twilio),
`sns` (SNS) and `(dev | test) & !twilio & !sns` (logging sender). With none of `dev`, `test`, `twilio` or `sns`
active, `auth-server` refuses to start (`MissingSmsGatewayConfiguration`), so a deployment never keeps its messages in
memory by mistake. A deployment therefore always activates `twilio` or `sns`.

== Keeping this page complete

`spring-boot-configuration-processor` is declared in the root `pom.xml`, so each module with a
`@ConfigurationProperties` record writes `target/classes/META-INF/spring-configuration-metadata.json` at build time.
Those files list every key of the records and can serve as a checklist when a property is added. They do not capture
the defaults set in compact constructors, nor the keys read with `@Value`, `@ConditionalOnProperty`,
`Environment.getProperty` or a `@Scheduled` cron placeholder (`authserver.keys.*`, `authserver.tokens.cleanup.*`,
`authserver.account.cleanup.cron`, `authserver.ott.cleanup.cron`, `authserver.password.compromised-check.enabled`,
`authserver.par.enabled`, `authserver.oidc.client-registration.enabled`, ...). Check those by hand in the code and in
the `application*.yml` files.
