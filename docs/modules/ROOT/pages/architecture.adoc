== Hexagonal layout

Each application is a Maven sub-reactor split into modules by hexagonal layer. The layering is enforced twice: by
`maven-enforcer-plugin` `bannedDependencies` rules in each module's `pom.xml` (jar granularity) and by a
`HexagonalArchitectureTest` (ArchUnit) in each application's `boot` module (package granularity).

[source,text]
----
<app>/                          aggregator pom, artifactId <app>-parent
  domain/                       <app>-domain
  application/                  <app>-application
  infrastructure/<adapter>/     <app>-infrastructure-<adapter>   (driven adapters: persistence, keys, ...)
  api/<adapter>/                <app>-api-<adapter>              (driving adapters: web, ...)
  boot/                         <app>-boot                       (composition root, the only runnable artifact)
----

[cols="1,2,2",options="header"]
|===
|Module
|May depend on
|Must not contain

|`domain`
|Nothing but the JDK (and Lombok, compile-only)
|Spring, Jackson, JPA/JDBC or Spring Security types

|`application`
|`domain` and Spring (use cases are `@Service` beans found by component scanning)
|Spring Security types, or any `infrastructure/*` or `api/*` module

|`infrastructure/*`
|`domain`, `application`
|A sibling adapter or any `api/*` module

|`api/*`
|`domain`, `application`
|Any `infrastructure/*` module

|`boot`
|Everything
|Business logic: it only wires beans, holds `application*.yml` and the integration tests
|===

A layer is only created once it has code: `bff` has `api/web` (the security, login, logout and relay adapters),
`infrastructure/session` (the Spring Session JDBC store, its cookie and its Flyway migration) and `boot` (the SPA), and no
`domain` or `application` module because it has no use case yet,
`resource-server` has `domain`, `application`, `infrastructure/memory` and `api/web`, and
`service-client` is a single `boot` module. A port is an interface in `domain` (for example `UserAccountRepository`);
its implementation lives in an `infrastructure/*` adapter. Domain models are never returned from a controller: the
`api/*` adapter maps them onto its own DTOs. Spring Security and Spring Authorization Server types are framework
adapters and live in `api/*` or `infrastructure/*`.

The REST APIs are contract first. Each application's OpenAPI contract lives under `apis/` at the repository root
(`apis/<app>/rest-server/<app>-api-v1.yaml`); `openapi-generator` turns it into Spring interfaces and DTO records in
the `api/web` module at build time (`target/generated-sources`, never committed), and the hand-written controllers
implement those interfaces by calling use cases. A `@Component` mapper per feature (for example `ClientDtoMapper`)
converts between the generated DTOs and the domain. `OpenApiDriftIT`, in each `boot` module, fails when the running
application serves an operation, status code or schema the contract does not declare. `apis/README.md` describes the
layout, the generator options and how to version a contract.

`test-support` (shared Testcontainers base), `e2e-tests` (Playwright) and `coverage` (JaCoCo aggregate) are root
modules outside the applications.

== Security filter chains

`auth-server` defines three `SecurityFilterChain` beans (module `auth-server/api/web`). `ApiSecurityConfig` (order 0)
secures `/api/**` statelessly: it validates bearer JWTs issued by this server itself for the API audience, with a
decoder of its own (see xref:tokens-and-keys.adoc[]), leaves registration, e-mail verification and password reset
public (rate limited), and requires the scope `admin` under `/api/admin/**`. In `SecurityConfig`, the first chain (order 1) applies only to the
authorization server protocol endpoints; the second (order 2) secures everything else, including the login page.

== Extension points for authentication methods

A feature spans the layers with the same package name in each (`...domain.password`, `...application.password`,
`...infrastructure.persistence.password`, `...api.web.password`), so authentication methods can be developed in
parallel. These extension points avoid editing shared files:

* `LoginChainCustomizer` (package `api.web.login`) is a functional interface over `HttpSecurity` (deliberately not a `Customizer<HttpSecurity>`, which Spring Security would apply to every chain). Every bean of this type is applied
  to the login chain in `@Order` order, before its catch-all rule.
* `LoginMethodFragment` contributes a Thymeleaf fragment to the login page (`templates/login.html`); the username and
  password form is the fragment in `templates/password.html`. See xref:login-and-bff.adoc[].
* `ProtocolChainCustomizer` (package `api.web`) is the same idea for the protocol endpoints: every bean receives the
  `OAuth2AuthorizationServerConfigurer` of the protocol chain, in `@Order` order. It is how the UserInfo mapper and the
  optional dynamic client registration are configured. It is also deliberately not a `Customizer`, which Spring
  Security would apply to every chain.
* `JwtClaimsContributor` (package `api.web.tokens`) adds claims to issued tokens: access tokens of both formats and ID
  tokens; see xref:tokens-and-keys.adoc[].

== BFF and resource server

The `bff` is an `oauth2Login()` client using the authorization code grant with PKCE. It keeps the user's tokens in a
server-side session (Spring Session JDBC, cookie `__Host-SESSION`), protects state-changing requests with CSRF
(`XSRF-TOKEN` cookie, `X-XSRF-TOKEN` header or `_csrf` form parameter), serves the SPA, exposes `GET /bff/user` and
`GET /bff/login`, lets Spring Security's logout filter answer `POST /bff/logout` with a redirect to the RP-initiated
logout of the authorization server, and relays `/api/**` calls to the resource server with the access token of the user. It is described
in xref:login-and-bff.adoc[].

one of the configured audiences (`resource-server` by default). Its API and security are described in
