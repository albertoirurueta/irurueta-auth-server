= Data model

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

`auth-server` stores its state in PostgreSQL. Flyway applies the migrations in
`auth-server/infrastructure/persistence/src/main/resources/db/migration` (`classpath:db/migration`) at start.

[cols="1,3",options="header"]
|===
|Migration
|Content

|`V100__spring_authorization_server_schema.sql`
|Tables of Spring Authorization Server: `oauth2_registered_client`, `oauth2_authorization_consent` and
`oauth2_authorization`.

|`V101__users.sql`
|Tables `users`, `user_authorities` and `user_passwords`.

|`V200__account.sql`
|Adds `email`, `email_verified` and `tenant` to `users`, and the `account_tokens` table (hashed single-use tokens).

|`V210__signing_keys.sql`
|Table `signing_keys` (public JWK, encrypted private JWK, status `NEXT`/`ACTIVE`/`RETIRED`); at most one `ACTIVE` key.

|`V230__consumed_refresh_tokens.sql`
|Table `consumed_refresh_tokens`, the hashes of rotated-out refresh tokens used for reuse detection.
|===

Each issue owns a range of migration numbers so features never collide: the walking skeleton uses `V100`-`V199` and the credential and token core (issue #2) uses `V200`-`V299`. A
migration is never written outside the range of the issue that adds it.
