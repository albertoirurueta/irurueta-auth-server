= Data model

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

`auth-server` stores its state in PostgreSQL. Flyway applies the migrations in
`auth-server/infrastructure/persistence/src/main/resources/db/migration` (`classpath:db/migration`) at start.

[cols="1,3",options="header"]
|===
|Migration
|Content

|`V100__spring_authorization_server_schema.sql`
|Tables of Spring Authorization Server: `oauth2_registered_client`, `oauth2_authorization_consent` and
`oauth2_authorization`.

|`V101__users.sql`
|Tables `users`, `user_authorities` and `user_passwords`.

|`V200__account.sql`
|Adds `email`, `email_verified` and `tenant` to `users`, and the `account_tokens` table (hashed single-use tokens).

|`V210__signing_keys.sql`
|Table `signing_keys` (public JWK, encrypted private JWK, status `NEXT`/`ACTIVE`/`RETIRED`); at most one `ACTIVE` key.

|`V230__consumed_refresh_tokens.sql`
|Table `consumed_refresh_tokens`, the hashes of rotated-out refresh tokens used for reuse detection.

|`V240__authorization_created_at.sql`
|Adds `created_at` to `oauth2_authorization`, so the authorizations that never got a token (abandoned authorization
or consent requests) can be cleaned up once they are old enough.

|`V400__mfa_security_events.sql`
|Security events and the failed second-factor attempts used for lockout (see xref:mfa-and-step-up.adoc[]).

|`V410__totp_recovery_codes.sql`
|TOTP secrets and recovery codes.

|`V420__trusted_devices.sql`
|Devices trusted to skip the second factor.

|`V500__webauthn.sql`
|Spring Security's WebAuthn tables (`user_entities`, `user_credentials`) and an index on the credential owner (see xref:passkeys.adoc[]).

|`V600__one_time_tokens.sql`
|Spring Security's `one_time_tokens` table for magic-link tokens (see xref:one-time-tokens.adoc[]).

|`V610__ott_codes.sql`
|Hashed numeric e-mail / SMS codes with their attempt counters.

|`V620__user_phones.sql`
|Verified E.164 phone numbers (one per user) and pending phone verifications.

|`V630__sms_cost_ledger.sql`
|Spend ledger used by the SMS cost caps.

|`V700__federated_identities.sql`
|Linked external identities (provider and subject unique per user), see xref:social-login.adoc[].

|`V701__generated_passwords.sql`
|Flags a generated (unknown) password, so a just-in-time account does not count a password as a sign-in method.

|`V710__x509_certificates.sql`
|Client certificate bindings by SHA-256 fingerprint, see xref:x509.adoc[].

|===

Each issue owns a range of migration numbers so features never collide: the walking skeleton uses `V100`-`V199` and the credential and token core (issue #2) uses `V200`-`V299`; multi-factor authentication (issue #4) uses `V400`-`V499`; passkeys (issue #5) use `V500`-`V599`; one-time tokens and SMS (issue #6) use `V600`-`V699`; social login, X.509 and the device grant (issue #7) use `V700`-`V799`. A
migration is never written outside the range of the issue that adds it.

== BFF database

The `bff` has its own PostgreSQL database (`bff`, created by `compose/init-databases.sql` in development), separate from
the one of `auth-server`. Its single Flyway migration, `V300__spring_session.sql` in
`bff/infrastructure/session/src/main/resources/db/migration`, creates the Spring Session JDBC tables `spring_session` (one row per browser
session) and `spring_session_attributes` (the serialized session attributes, among them the authorized OAuth2 client with
the user's tokens). Spring Session never creates them (`initialize-schema: never`). The schema and its use are described
in xref:login-and-bff.adoc[].
