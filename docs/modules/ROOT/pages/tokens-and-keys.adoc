== Persisted, rotating signing keys

Signing keys are RSA keys (`RS256`) stored in the `signing_keys` table with a status of `NEXT`, `ACTIVE` or `RETIRED`.
The private half is encrypted with AES-256-GCM (`Encryptors.stronger`) using a password and salt from
`authserver.keys.encryption.password` and `authserver.keys.encryption.salt`, which come from the environment in
production and are never committed. With the `dev` profile, a random secret is created once under
`~/.irurueta-auth-server/` (readable by the owner only) and reused, so persisted keys survive restarts.

`RotateSigningKeysUseCase` applies the lifecycle: it creates the `ACTIVE` and `NEXT` keys when missing, promotes
`NEXT` and retires the old `ACTIVE` key when the rotation interval has elapsed, always leaves a fresh `NEXT` key, and
deletes keys retired for longer than the retention. Rotation runs in one transaction guarded by a PostgreSQL advisory
lock, so two instances never rotate at once.

== Token contents

`RolesTenantAudienceTokenCustomizer` adds the `roles`, `tenant` and `aud` claims to access tokens. The audience is the
logical API identifier configured per client (client setting `audiences`, default the client id).
Other features add claims, for example `amr` or `acr`, without editing it, by declaring `JwtClaimsContributor`
beans, applied in `@Order` order.

== Refresh token reuse detection

Refresh tokens rotate. A decorator over `OAuth2AuthorizationService` records the hash of every rotated-out refresh
token in `consumed_refresh_tokens`; presenting one of them revokes the whole authorization, because the token was
stolen or replayed.
