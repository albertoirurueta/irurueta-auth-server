== Persisted, rotating signing keys

Signing keys are RSA keys (`RS256`) stored in the `signing_keys` table with a status of `NEXT`, `ACTIVE` or `RETIRED`.
The private half is encrypted with AES-256-GCM (`Encryptors.stronger`) using a password and salt from
`authserver.keys.encryption.password` and `authserver.keys.encryption.salt`, which come from the environment in
production and are never committed. With the `dev` profile, a random secret is created once under
`~/.irurueta-auth-server/` (readable by the owner only) and reused, so persisted keys survive restarts.

`RotateSigningKeysUseCase` applies the lifecycle: it creates the `ACTIVE` and `NEXT` keys when missing, promotes
`NEXT` and retires the old `ACTIVE` key when the rotation interval has elapsed, always leaves a fresh `NEXT` key, and
deletes keys retired for longer than the retention. The start-up runner and `SigningKeyRotationJob` call `execute()`,
which only rotates a key that is due; `POST /api/admin/keys/rotate` calls `executeForced()`, which retires the active
key now whatever its age (for example after a suspected compromise). Rotation runs in one transaction guarded by a
PostgreSQL advisory lock, so two instances never rotate at once.

A retired key must stay published for as long as any token it signed can still be presented. `SigningKeyRetention`
therefore computes the *effective* retention as the longest of the configured retention and the longest signed-token
lifetime plus the clock skew. The signed tokens are the access tokens of the clients with self-contained tokens and
the ID tokens (reported by the `SignedTokenLifetimes` port, implemented over the registered clients by
`RegisteredClientTokenLifetimes`; Spring Authorization Server fixes the ID-token lifetime at 30 minutes) and the
24-hour e-mail verification tokens. Registering a client with longer-lived tokens lengthens it automatically.

== Bearer tokens of the API

The `/api/**` chain (`ApiSecurityConfig`) has a decoder of its own, separate from the one the UserInfo endpoint uses.
It accepts a token only when this server signed it (published keys), its issuer is this server, its timestamps are
valid, its `aud` lists the API audience (`authserver.api.audience`, default `auth-server`) and it does not carry the
`purpose` claim of the account tokens, so a user's access token for the resource server, or an e-mail verification
JWT, is answered `401`. `/api/admin/**` needs the `admin` scope; the `ADMIN` role alone does not open it. The seeded
`bff` and `spa-public` clients carry the API audience (so their users can change their password) but never the
`admin` scope.

== Token contents

`IssuedTokenClaims` adds the `roles`, `tenant` and `aud` claims to access tokens, whatever their format. The audience
is the logical API identifier configured per client (client setting `audiences`, default the client id).
`RolesTenantAudienceTokenCustomizer` applies it to the JWTs (access and ID tokens) and
`ReferenceTokenClaimsCustomizer` to the claims stored for a reference (opaque) access token, which the introspection
endpoint returns, so a resource server that introspects sees the same claims as one that decodes a JWT. Other
features add claims, for example `amr` or `acr`, without editing them, by declaring `JwtClaimsContributor` beans,
applied in `@Order` order to the access tokens of both formats and to the ID tokens (a contributor checks
`context.getTokenType()` when a claim belongs to one kind only). ID tokens get the contributed claims but none of
`roles`, `tenant` or `aud`.

== Refresh token reuse detection

Refresh tokens rotate. A decorator over `OAuth2AuthorizationService` records the hash of every rotated-out refresh
token in `consumed_refresh_tokens`; presenting one of them revokes the whole authorization, because the token was
stolen or replayed.
