= X.509 client certificates

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

A user can sign in with a client certificate from the button the login page shows, which posts to `POST /login/x509`
with the CSRF token (a Spring Security filter endpoint, so it is not in the pages contract). A `GET` of that path never
signs anybody in, and a post without the token is refused before the certificate is looked at, so a page of another
site cannot make a browser sign in with the certificate it holds. The feature is off unless `authserver.x509.enabled`
is true. A certificate is bound to an account by its SHA-256 fingerprint (never committed, never generated by the
build: tests and the `dev` profile create theirs at run time with `keytool`).

== Binding certificates through the account API

A user binds and unbinds certificates with the bearer-protected account API: `GET /api/account/certificates` lists
them, `POST /api/account/certificates` binds the PEM certificate of its JSON body (only the public certificate, within
its validity period; a value that carries a private key is refused without being parsed) and
`DELETE /api/account/certificates/\{id}` unbinds one. Binding and unbinding change how the account signs in, so both
call `StepUpGuard` first, as unlinking an identity does. Unbinding is refused (`409 last-sign-in-method`) when the
certificate is the last way to sign in, counted under the same per-account lock as unlinking an identity (see
xref:social-login.adoc[Social login]). The API exists whether or not the sign-in with a certificate is enabled.

== Factor and chain

`FACTOR_X509` is a strong primary factor whose `amr` value is `sc` (smart card) or `hwk` (hardware-bound key), from
`authserver.x509.amr`. It lets the user in without a second factor, but it is not multi-factor alone (a certificate is
possession of a key, and the server cannot tell whether a PIN protected it): a certificate-only session gets the
password `acr`, so a step-up (`acr_values` for the multi-factor class, or the account API's `StepUpGuard`) asks for a
second factor (see xref:mfa-and-step-up.adoc[]).

== The button on the login page

`X509LoginMethodFragment` is a `LoginMethodFragment` (order 260, after the social providers): a form with one button
whose action depends on the transport. With a proxy that forwards the certificate it is the relative path. With only the
dedicated TLS port, a page served on any other port posts to `https://<same host>:<port>/login/x509`, the one port that
asks for a certificate; a page served on the TLS port itself posts to the relative path. Cookies belong to a host, not
to a port, so the session and its CSRF token are valid on both ports, but browsers count `http` and `https` as
different sites and do not send a `SameSite` cookie on a post from one to the other: serve the main port over `https`
too, or open the login page on the TLS port (as the development setup does, whose main port is plain `http`). The login
page has no `form-action` directive in its Content Security Policy, so the post to the other port is not blocked.

== Two transports, one extractor

A reverse proxy can forward the certificate in a header. The filter reads it only for a request from one of
`trusted-proxies`, parses it and sets the servlet request attribute the framework filter reads, so a spoofed header
from anyone else is ignored.

The address compared with `trusted-proxies` is `getRemoteAddr()`, the address left once Spring Boot has handled the
forwarded headers. Only with `server.forward-headers-strategy: none` is that the direct network peer. With `framework`,
Spring's `ForwardedHeaderFilter` replaces it with the first `X-Forwarded-For` value, which any client can send (naming
a trusted proxy there would make a forged certificate header look trusted); with `native`, Tomcat's `RemoteIpValve`
replaces it with the client the proxies report, so the proxy itself is never seen. A strategy that is not set defaults
to `native` on a cloud platform Spring Boot detects. `X509ForwardedHeadersGuard` therefore stops the startup when a
`forwarded-header` is configured with any strategy but `none` (an empty `trusted-proxies` is already refused by
`X509Properties`). The proxy may still send `X-Forwarded-*` headers; the authorization server does not use them, so
its public URLs (the issuer) must be configured explicitly.

advertises no certificate authority and accepts any chain, because the JVM default would advertise only its own CAs and a
client holding a certificate from a private CA would never offer it. The identity is the bound fingerprint and the
validity period, not the chain, and there is no CRL or OCSP check.
