== Password storage

Passwords are stored by a `DelegatingPasswordEncoder` whose default is *Argon2id* (`{argon2@SpringSecurity_v5_8}`);
bcrypt and PBKDF2 hashes keep working. The encoder is a framework type, so it lives in `api/web`
(`PasswordConfiguration`); the `application` layer reaches it through the `PasswordHasher` port of the `domain`.

== Password policy and compromised passwords

`PasswordPolicy` (module `domain`) requires between 12 and 128 characters. New passwords are also checked against the
Have I Been Pwned range API (only a hash prefix leaves the server) through the `CompromisedPasswordCheck` port. The
check is on by default; set `authserver.password.compromised-check.enabled=false` to turn it off, for example offline.
Tests mock the port.

== Account API

`AccountController` exposes the account operations under `/api/account`. They are defined by the contract
`apis/auth-server/rest-server/auth-server-api-v1.yaml`: `AccountController` implements the `AccountApi` interface
generated from it (see `apis/README.md`).

[cols="2,1,3",options="header"]
|===
|Endpoint
|Access
|Behavior

|`POST /api/account/register`
|Public, rate limited
|Creates a disabled-until-verified account and e-mails a verification link (a signed JWT). The answer is always the same `202` (see <<registration-enumeration>>). If the e-mail cannot be sent, nothing is registered and the answer is `503`.

|`GET /api/account/verify`
|Public, rate limited
|Verifies the e-mail address with the token from the link and enables the account. A link works once: replayed, even before it expires, it is answered as an invalid token, so it can never re-enable an account that was disabled after its verification.

|`POST /api/account/password`
|Bearer token for the API audience
|Changes the password of the caller after checking the current one, and revokes every authorization of the user in the same transaction.

|`POST /api/account/password/reset-request`
|Public, rate limited
|E-mails a reset link to a registered address. An unknown address is never mailed, so the endpoint cannot be used to send mail to arbitrary addresses; it costs the same token work and gets the same `202`, even when a link cannot be delivered.

|`POST /api/account/password/reset`
|Public, rate limited
|Sets a new password with a single-use reset token and revokes every authorization of the user. Every check (token, password policy including the username rule, compromised-password check) runs before the token is consumed, so a rejected password does not use up the link.
|===

The reset token is a random opaque value stored only as a hash, with an expiry and a used timestamp, in the
`account_tokens` table (see xref:data-model.adoc[]). `ExpiredAccountTokenCleanupJob` deletes the expired ones
(`authserver.account.cleanup.cron`, default `0 30 * * * *`).

Every use case that changes several rows runs in one transaction (`@Transactional`): the new password hash and the
revocation of the user's authorizations, the consumed reset token and the new hash, the new account and its e-mail.
The mail adapter reports a delivery failure as an `AccountMailException` (never the mail framework's own type), so the
transaction rolls back and nothing is left for a message that was never sent.

[[registration-enumeration]]
=== Registration never reveals a taken address or username

The answer of `POST /api/account/register` is the same in every case, and the password is always hashed, so neither
the answer nor its timing tells whether the address or the username exists. What the address receives differs only
where its owner learns nothing new:

* a registered address gets an "already registered" message: its owner already knows it has an account;
* a new address with a taken username gets the usual verification message, but its token names no account, so
following the link fails exactly like an expired one. Nothing is created, and the username is never confirmed to
whoever controls the address.

== Rate limiting

The unauthenticated account endpoints (register, verify, reset request, reset) are rate limited by
`AccountRateLimiter` in `api/web`: requests are counted in fixed windows per client address and, when the request
names one, per e-mail address, so neither a single client nor many clients aiming at one address can flood mailboxes
or guess reset tokens. A request over a limit gets `429 Too Many Requests`, a problem detail
(`urn:problem:account:rate-limited`) and a `Retry-After` header in seconds. The counters are in memory and bounded
(the oldest key is forgotten first); each instance applies the limits on its own. The client address is
`request.getRemoteAddr()`, so behind a reverse proxy set `server.forward-headers-strategy`.

[cols="2,1,3",options="header"]
|===
|Property
|Default
|Meaning

|`authserver.account.rate-limit.enabled`
|`true`
|Whether the limits apply at all.

|`authserver.account.rate-limit.window`
|`PT15M`
|Length of the window the requests are counted in.

|`authserver.account.rate-limit.per-client`
|`20`
|Requests one client address may make in a window.

|`authserver.account.rate-limit.per-email`
|`5`
|Requests that may name one e-mail address in a window.

|`authserver.account.rate-limit.max-tracked-keys`
|`10000`
|Counters kept at most per kind of key.
|===
