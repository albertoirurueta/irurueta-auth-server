= Login pages and the BFF

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

This page describes the server-rendered pages of `auth-server` (login, consent, logout) and how the `bff` signs users in
for a single page application (SPA) without ever exposing a token to the browser.

== Login page

The pages are Thymeleaf templates under `auth-server/api/web/src/main/resources/templates`. They share one layout
(`fragments/layout.html`) that renders the branding header and footer, and load a stylesheet from the same origin: there
is no inline script or style, which is what lets the content security policy be strict. The text comes from
`messages.properties` (English; `spring.web.locale: en` and no fallback to the system locale, so the language never

=== Security headers

`LoginHeadersCustomizer` adds `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'` (same-origin
resources only, no framing), `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` to the pages of the
login chain.

The policy has deliberately no `form-action` directive. Browsers also apply it to the redirects that follow a form
submission, so `form-action 'self'` blocked (in Chromium) the redirect from the login or consent form back to the client
application's `redirect_uri`, which is on another origin.

== Consent page

The authorization endpoint is pointed at the custom consent page (`ConsentProtocolCustomizer`) instead of the generated
one. The page lists the requested scopes with a description each, as checkboxes that are checked by default, and the
scopes already granted. *Allow* posts the approved scopes back to `/oauth2/authorize`; *Deny* posts none, which the
authorization endpoint answers with `error=access_denied`, and the BFF then shows a sign-in failure.

Consent is a property of the registered client: `requireConsent` in the client registration and in the clients API
(`POST` and `PUT /api/admin/clients`; default `false`). The default `bff` client requires it, `spa-public` does not.

== Logout

[cols="2,1,3",options="header"]
|===
|Mechanism
|Support
|Notes

|RP-initiated logout (`/connect/logout`)
|Supported
|Provided by Spring Authorization Server with OpenID Connect enabled. A client may only send the user to a
`post_logout_redirect_uri` listed in its registered `postLogoutRedirectUris`; any other is never honoured. They are
seeded from `authserver.clients.<client>.post-logout-redirect-uris` (`AUTHSERVER_BFF_POST_LOGOUT_REDIRECT_URIS`,
`AUTHSERVER_SPA_POST_LOGOUT_REDIRECT_URIS`) and are part of the clients API.

|Back-channel logout
|Not implemented
|The server sends no `logout_token` to the clients, so a client session survives a sign-out of the server until it
expires or the user signs out of the client too.

|Front-channel logout
|Not supported
|Spring Authorization Server does not support it.
|===

The server also has its own sign-out for users of its login pages: a confirmation page (`logout.html`) whose form posts
to `/logout`. The POST carries the CSRF token (`th:action` adds it), so a third-party page cannot sign the user out; it
invalidates the session, deletes the `JSESSIONID` cookie and returns to `/login?logout`.

== Backend for frontend

The `bff` (port 8080) is the only client the browser talks to. It serves the SPA (static files from its `boot` module),
runs the authorization code flow with PKCE as a confidential client, keeps the user's tokens in its server-side session
and attaches the access token to the calls the SPA makes to the resource server. The browser holds nothing but a session
cookie: the end-to-end test scans storage, cookies and response bodies to prove that no token is visible.

[source,java]
----
include::example$bff/api/web/src/main/java/com/irurueta/authserver/bff/api/web/security/SecurityConfig.java[tag=bff-security]
----

Requests under `/bff/**` and `/api/**` that are not authenticated get a `401` instead of a redirect, so the SPA can
decide what to do. A failed or denied sign-in redirects to `/?error=signin`. The BFF chain sets the same content security
policy as the login pages.

=== Session and cookie

The HTTP session is stored in PostgreSQL by Spring Session JDBC, in the `bff` database. The schema is owned by Flyway
(`V300__spring_session.sql`; Spring Session never creates it). The session holds the authorized client, that is, the
access and refresh tokens (`HttpSessionOAuth2AuthorizedClientRepository`), so the sessions survive a restart and the
tokens never leave the server.

The cookie is `__Host-SESSION`: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` and no `Domain`, which is exactly what the
`__Host-` prefix makes browsers require. Chromium accepts `Secure` cookies on `http://localhost`, so local development

=== CSRF

The SPA recipe is used: `csrf.spa()` stores the token in the `XSRF-TOKEN` cookie, readable by scripts, and accepts it
from the `X-XSRF-TOKEN` request header. Spring Security loads the token lazily, so `CsrfCookieFilter` reads it on every
request to make sure the cookie is always written. The SPA script copies the cookie into the header of every
state-changing request.

=== Login and logout API

`GET /bff/login?returnTo=` starts the sign-in. `returnTo` is only accepted when it is an allow-listed relative path
(`bff.login.allowed-return-paths`, an entry ending in `/` also allows what is below it), otherwise the answer is `400`;
this prevents an open redirect. The accepted target is stored as the saved request of the session, so the OAuth2 login
success handler sends the browser there, and the browser is redirected to the authorization request.

=== Token relay

Calls to `/api/**` (GET, POST, PUT, PATCH, DELETE) are forwarded to the resource server (`bff.relay.target-uri`,
`RESOURCE_SERVER_URI`) with the access token of the user of the session as bearer token; the browser never sends or sees
it.

The relay is a `RestClient` with Spring Security's `OAuth2ClientHttpRequestInterceptor`, written in this repository,
rather than Spring Cloud Gateway's token relay. No Spring Cloud release train supports Spring Boot 4.1 yet: the latest
released train (2025.1.x) is built on Boot 4.0, and the one for Boot 4.1 (2026.0.0) is not released. When one is, the
relay can be replaced by the gateway's filter.

The interceptor asks the authorized client manager for the token, renewing it with the refresh token when it expired. It
lets a call through unauthenticated when the session has no authorized client, so a second interceptor stops that call:
the relay never sends a request without a token. When the token cannot be obtained or renewed the answer is `401`, so
the SPA signs in again; when the resource server cannot be reached it is `502`.

=== The single page application

The SPA is `index.html` plus `assets/app.js`, served by the BFF itself so that everything is same-origin, which the
content security policy requires (no inline script). It asks `GET /bff/user` for the session, shows the profile or a
sign-in link to `/bff/login?returnTo=%2F`, calls `/api/documents` through the relay and signs out through
`POST /bff/logout`.
