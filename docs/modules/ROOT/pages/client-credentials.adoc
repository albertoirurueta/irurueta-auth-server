= Client credentials and service-to-service calls

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

`service-client` is a command-line application that calls the resource server as a client, not as a user. It has the
hexagonal layout of the other applications: `domain` (the `Document` model and the ports `DocumentGateway` and
`OnBehalfOfDocumentGateway`), `application` (`ListDocumentsUseCase`, `ListDocumentsOnBehalfOfUseCase`),
`infrastructure/resourceserver` (the only module with Spring Security and the client generated from the resource
server's contract) and `boot` (one runner per profile). Profiles: `device-flow` (see xref:device-grant.adoc[]),
`client-credentials` and `token-exchange`.

== Client credentials

The `client-credentials` profile (`ClientCredentialsCli`) obtains a token with the `client_credentials` grant and lists
`GET /api/documents`. The token is cached by an `AuthorizedClientServiceOAuth2AuthorizedClientManager` and renewed
when less than `service-client.auth.refresh-before` (default `PT60S`) of its life is left.

Settings come from the environment (`SERVICE_CLIENT_ID`, `SERVICE_CLIENT_SECRET`, `SERVICE_CLIENT_TOKEN_URI`,
`SERVICE_CLIENT_RESOURCE_SERVER_URI`, `SERVICE_CLIENT_AUTH_METHOD`, `SERVICE_CLIENT_DPOP`). With
`SERVICE_CLIENT_PRINT_ACCESS_TOKEN=true` the access token is printed too.

== Client authentication methods

[cols="2,3",options="header"]
|===
|`service-client.auth.method`
|How the client proves its identity

|`client_secret_basic`
|The registered secret, in the HTTP Basic header.

|`private_key_jwt`
|A signed assertion (RFC 7523). The key is an unencrypted PKCS#8 PEM in `SERVICE_CLIENT_PRIVATE_KEY` or a file path;
the server holds only the public JWK set (`jwks` of the client) or a `jwkSetUrl`. No key is committed anywhere.

|`tls_client_auth`
|The client certificate of a mutual-TLS connection (RFC 8705), taken from the SSL bundle named by `ssl-bundle`.

|`self_signed_tls_client_auth`
|A self-signed certificate pinned through the client's registered JWKs (`x5c`).
|===

=== Server side

A client assertion must carry `jti` and `iat` and live at most `authserver.client-assertion.max-lifetime`
(default `PT5M`); Spring Authorization Server requires neither and has no replay store, so the server adds both.
Each `(client_id, jti)` is recorded once in `client_assertion_jtis` and a replay is refused with `invalid_client`.

`tls_client_auth` validates the presented chain by PKIX against `authserver.mtls.trusted-authorities` before comparing the
subject DN; with none configured the method is refused. The dedicated TLS port accepts any chain so that clients of
private authorities can present one, which makes this check the trust decision.

WARNING: The PKIX validation does not check revocation (no CRL or OCSP).

== Certificate-bound and DPoP-bound tokens

A client registered with `certificateBoundAccessTokens` gets `cnf.x5t#S256` in its tokens; a token request carrying a
DPoP proof gets `token_type=DPoP` and `cnf.jkt`. The resource server rejects a bound token used without the matching
certificate or proof (see xref:resource-server.adoc[]). Spring Security has no client-side DPoP, so `service-client`
builds its proofs with Nimbus (`DPoPProofs`).

== Token exchange (RFC 8693)

The `token-exchange` profile (`TokenExchangeCli`) takes the access token of a user from `SERVICE_CLIENT_SUBJECT_TOKEN`,
uses its own client-credentials token as the `actor_token` and calls `GET /api/documents` as that user: `sub` stays the
user and the token carries `act.sub` = the service client. The client needs the grant
`urn:ietf:params:oauth:grant-type:token-exchange`.
