= Refresh token rotation and reuse detection

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

A client that holds a refresh token trades it at the token endpoint for a new access token. The default clients rotate
refresh tokens (`reuseRefreshTokens` false), so every refresh also returns a *new* refresh token and the old one stops
working. Spring Authorization Server does the rotation; this repository adds reuse detection on top:
`ReuseDetectingAuthorizationService`, a decorator of the JDBC `OAuth2AuthorizationService`, records the SHA-256 hash of
each rotated-out refresh token in `consumed_refresh_tokens`. If one of those tokens is ever presented again, the token
was stolen or replayed, so the whole authorization is deleted: the attacker's token and the legitimate client's
current refresh and access tokens all stop working.

|Preconditions
|The client was issued a refresh token by an earlier grant (for `bff`, the authorization code grant).

|Endpoints
|`POST /oauth2/token` with `grant_type=refresh_token`. The same detection applies to any lookup of a refresh token
without a token type, as `/oauth2/revoke` and `/oauth2/introspect` make when no `token_type_hint` is sent.

|Storage
|`oauth2_authorization` (Spring Authorization Server schema, `V100`) and `consumed_refresh_tokens` (`V230`, foreign key
to `oauth2_authorization` with `ON DELETE CASCADE`).

== Steps

=== Normal refresh

. The client posts `grant_type=refresh_token&refresh_token=RT1` to `/oauth2/token`, authenticating as usual
(`client_secret_basic` for `bff`). In the `bff` this happens inside `OAuth2AuthorizedClientManager`, called by
`OAuth2ClientHttpRequestInterceptor` when the access token of the session has expired.
. Spring Authorization Server calls `findByToken(RT1, refresh_token)`. The delegate finds the authorization, so the
decorator returns it unchanged.
. The framework checks that the refresh token belongs to this client and is active, then generates a new access token,
a new refresh token `RT2` (rotation) and, when `openid` was granted, a new ID token.
. It calls `save(authorization)`. The decorator reads the stored version first (`findById`), saves the new one through
the delegate and, because the refresh token value changed from `RT1` to `RT2`, inserts the hash of `RT1` with the
authorization id into `consumed_refresh_tokens` (`ON CONFLICT DO NOTHING`).
. The client receives the new access token and `RT2`, and must drop `RT1`.

=== Reuse of a rotated token

. Someone presents `RT1` again (an attacker with a copy, or a client that kept the old value).
. `findByToken(RT1, refresh_token)` finds nothing in `oauth2_authorization`, because the stored authorization now
holds `RT2`.
. The decorator hashes `RT1` and looks it up in `consumed_refresh_tokens`. It finds the authorization id, logs a warning
(`A rotated refresh token was presented again; revoking the authorization ...`) and removes that authorization through
the delegate. Its `consumed_refresh_tokens` rows go with it (cascade).
. The decorator returns `null`, so the token endpoint answers `400 invalid_grant`.
. When the legitimate client next refreshes with `RT2`, the authorization no longer exists and it also gets
`400 invalid_grant`. In the `bff`, `RestDocumentGateway` reports the failed renewal as unauthorized, the SPA gets `401`
and starts a new sign-in.

A token that was never issued, or whose authorization was already deleted (by a previous reuse or by
`ExpiredAuthorizationCleanupJob`), is simply unknown: `invalid_grant`, nothing revoked.

== Tokens and claims

The refresh response has the same shape as the authorization code response: a new `access_token` (same claims as
before, `roles`, `tenant`, `aud`, `scope`; `amr`, `acr` and `auth_time` keep describing the original sign-in), a new
`refresh_token`, `token_type`, `expires_in`, `scope` and, with the `openid` scope, a new `id_token`.

Only hashes are stored in `consumed_refresh_tokens`, so the table cannot be used to obtain tokens. Lookups of other
token types (access token, device and user codes) are forwarded unchanged.

== How it is tested

* `auth-server/boot` `TokenFlowIT`: `refresh_whenTokenIsValid_rotatesTheRefreshToken` (new access and refresh token,
one authorization) and `refresh_whenRotatedTokenIsReused_revokesTheAuthorization` (the replay is refused, the
authorization count drops to zero and the current refresh token is refused too); also revocation of a refresh token.
* `auth-server/infrastructure/persistence` `ReuseDetectingAuthorizationServiceIT`: over the JDBC service and PostgreSQL,
a replayed rotated token revokes the authorization, and a refresh token that is not rotated records nothing.
* `auth-server/infrastructure/persistence` `ReuseDetectingAuthorizationServiceTest`: unit tests of each branch (new
authorization, rotation, unchanged token, device and user codes forwarded unchanged, consumed and never-consumed tokens).
