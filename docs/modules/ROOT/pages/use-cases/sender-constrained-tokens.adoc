= Sender-constrained tokens

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

A bearer token works for whoever holds it. A sender-constrained token is bound to a key the client proves it holds, so a
stolen token alone is useless. Two bindings are implemented: DPoP, where the client signs a fresh proof JWT for every
request and the token carries the thumbprint of the proof key (`cnf.jkt`), and certificate-bound tokens, where the client
authenticates with mutual TLS and the token carries the thumbprint of its certificate (`cnf.x5t#S256`). The authorization
server side is Spring Authorization Server's; `service-client` hand-wires the client side of DPoP because Spring Security
has none; the resource server checks both bindings.

.At a glance
* *Actors*: `service-client`, `auth-server`, `resource-server`.
* *Clients involved*: a confidential client of `service-client` (see xref:use-cases/client-credentials.adoc[]).
* *Preconditions*:
** DPoP: nothing on the server or the client registration; `service-client.auth.dpop=true` (`SERVICE_CLIENT_DPOP`) on
   `service-client`.
** Certificate-bound: the client registered with `tls_client_auth` or `self_signed_tls_client_auth` and
   `certificateBoundAccessTokens: true`; the authorization server's TLS connector (`authserver.x509.enabled=true`,
   `authserver.x509.port`); the resource server served over TLS with `server.ssl.client-auth: want` and a bundle.
* *Endpoints*: `POST /oauth2/token`, `GET /api/documents`, the metadata endpoints
  `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration` (for `mtls_endpoint_aliases`).

== Steps

=== DPoP

. With `service-client.auth.dpop=true`, `OAuth2ClientConfiguration` declares a `DPoPProofs` bean over Nimbus'
  `DefaultDPoPProofFactory` with a P-256 key generated in memory at startup (signing algorithm `ES256`). Nothing is
  written to disk.
. `TokenEndpointClients` adds a `DPoP` header to every token request: a proof for `POST` and the token URI
  (`DPoPProofs.proof(method, uri)` drops the query and fragment, as `htu` requires).
. Spring Authorization Server validates the proof and issues `token_type=DPoP` with `cnf.jkt`, the JWK SHA-256
  thumbprint of the proof key.
. For each resource call, `ResourceServerInterceptors` installs `DPoPClientHttpRequestInterceptor`, which gets the token
  from the authorized client manager and, when its type is `DPoP`, sends `Authorization: DPoP <token>` and a new proof
  for the request's method and URL with `ath` (the hash of the token). A token the server issued as `Bearer` is sent as
  `Bearer`.
. The resource server's JWT chain enables `dPoP(...)`: it checks the proof's signature, that its key matches `cnf.jkt`,
  `htm`, `htu`, `ath`, its age and its `jti` against a replay cache. A DPoP-bound token sent as `Bearer` or without a
  proof is answered `401`.

=== Certificate-bound tokens

. The client opens a TLS connection to the authorization server's TLS port and presents its certificate (the SSL bundle
  named by `service-client.auth.ssl-bundle`, `SERVICE_CLIENT_SSL_BUNDLE`).
. It authenticates with `tls_client_auth` or `self_signed_tls_client_auth` (`ClientCertificateVerifier`, see
  xref:use-cases/client-authentication.adoc[]).
. Because the client has `certificateBoundAccessTokens`, the framework writes `cnf.x5t#S256`, the base64url SHA-256
  thumbprint of the certificate, into the access token.
. The client calls the resource server over TLS with the same certificate. The validator that Spring Boot's JWT decoder
  includes compares the thumbprint with the certificate of the connection; without it, or with another certificate,
  the answer is `401`.
. When `authserver.x509.port` is set, `MtlsEndpointAliases` adds `mtls_endpoint_aliases` to both metadata documents
  (through `ClientAuthProtocolChainCustomizer`): the token, revocation, introspection, pushed authorization request and
  device authorization endpoints as `https` URLs on that port, so a client knows where to send mutual TLS requests.

== Tokens and claims

* DPoP: the token response has `token_type=DPoP`; the access token has `cnf: {"jkt": "<JWK SHA-256 thumbprint>"}`.
* Certificate-bound: the access token has `cnf: {"x5t#S256": "<certificate SHA-256 thumbprint>"}`; `token_type` stays
  `Bearer`.
* All other claims are those of the grant (for client credentials: `sub` = client id, `aud`, `scope`).

== How it is tested

* `auth-server/boot`: `ClientAuthenticationIT` (`token_whenADpopProofIsSent_issuesADpopTokenBoundToTheProofKey`,
  `token_whenCertificateBoundAccessTokensAreEnabled_carriesTheCertificateThumbprint`).
* `resource-server/boot`: `BoundTokenIT` accepts a certificate-bound token only with its certificate, and a DPoP-bound token
  only with a valid proof from the bound key (refused as `Bearer`, without a proof or with a proof of another key).
* `service-client/infrastructure/resourceserver`: `ResourceServerAdapterIT`
  (`listDocuments_whenDPoPIsOn_sendsProofsAndTheDPoPScheme`); unit tests `DPoPProofsTest` and
  `DPoPClientHttpRequestInterceptorTest`.
* `e2e-tests`: `ClientCredentialsEndToEndIT` (`clientCredentials_whenTheToolUsesDpop_theTokenIsBoundToItsKey` and
  `clientCredentials_whenTheClientPresentsACertificateOfATrustedAuthority_theTokenIsBoundToTheCertificate`).
* `auth-server/api/web`: unit test `MtlsEndpointAliasesTest`.
