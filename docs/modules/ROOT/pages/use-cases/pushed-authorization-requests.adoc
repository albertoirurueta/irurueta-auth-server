= Pushed authorization requests

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

With pushed authorization requests (PAR, RFC 9126) the client sends the parameters of its authorization request straight
to the authorization server over an authenticated back-channel call, and the browser is then sent to the authorization
endpoint with only an opaque `request_uri`. The parameters can no longer be read or altered in the browser, the client
is authenticated before the user sees anything, and long requests do not hit URL limits. The endpoint is Spring
Authorization Server's; this repository only switches it on with a property. The rest is the ordinary authorization code
flow with PKCE (see xref:use-cases/authorization-code-bff.adoc[]).

.At a glance
* *Actors*: the user with a browser, a client of the authorization code flow, `auth-server`.
* *Clients involved*: any client with the `authorization_code` grant and a registered redirect URI. No client setting
  makes PAR mandatory: the endpoint is offered, not required. The BFF does not use it.
* *Preconditions*: `authserver.par.enabled=true` (default `false`). It is a property, not a profile.
* *Endpoints*: `POST /oauth2/par`, `GET /oauth2/authorize`, `POST /oauth2/token`; the metadata field
  `pushed_authorization_request_endpoint` in `/.well-known/openid-configuration` and
  `/.well-known/oauth-authorization-server`.

== Steps

. With `authserver.par.enabled=true`, `ParConfiguration` (conditional on the property) declares a
  `ProtocolChainCustomizer` (order 5) that enables the framework's pushed authorization request endpoint. The metadata
  then advertises `pushed_authorization_request_endpoint`; with the property off, `POST /oauth2/par` answers `404` and the
  field is absent.
. The client builds a normal authorization request (`response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`,
  `code_challenge`, `code_challenge_method=S256`) and posts it as a form to `POST /oauth2/par`, authenticating as it would
  at the token endpoint (see xref:use-cases/client-authentication.adoc[]).
. The server authenticates the client, validates the request as the authorization endpoint would (client, redirect URI,
  scopes, PKCE), stores it and answers `201 Created` with `request_uri`
  (`urn:ietf:params:oauth:request_uri:...`) and `expires_in`.
. The client redirects the browser to `GET /oauth2/authorize?client_id=...&request_uri=...`.
. The server resolves the stored request. From here the flow is the authorization code flow: sign-in at `/login`, the MFA
  policy and step-up (`MfaProtocolChainCustomizer` and `StepUpProtocolChainCustomizer` apply as usual, so a client with
  `mfaRequired` sends the user to `/login/second-factor`), consent, then a redirect to `redirect_uri` with `code` and
  `state`.
. The `request_uri` is single use: presenting it again does not yield another code.
. The client exchanges the code with its `code_verifier` at `POST /oauth2/token`.

== Tokens and claims

PAR changes how the request reaches the server, not the result: the tokens are those of the authorization code flow
(access token with `roles`, `tenant`, `aud` and the MFA claims, refresh token, and an ID token when `openid` was
requested). The push response holds only `request_uri` and `expires_in`.

== How it is tested

* `auth-server/boot`: `ParIT` checks that with the property off the endpoint answers `404` and is not advertised; with
  `authserver.par.enabled=true` it answers a `request_uri` and is advertised, the pushed request completes the code flow,
  a client requiring MFA is sent to the second-factor page, and a reused `request_uri` yields no code.
