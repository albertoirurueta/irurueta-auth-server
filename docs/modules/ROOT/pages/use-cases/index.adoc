= Use cases

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

The pages in this section walk through each OAuth 2.0 / OpenID Connect flow the example implements, step by step.
Each page names the actors and the clients involved, what must be configured first, the endpoints, the tokens and
claims it returns and the tests that exercise it, and shows the exchange as Mermaid sequence diagrams (with a
flowchart where the flow branches). Each one links to the official specification and to the matching page of the
{oauth-ref}/index.html[OAuth Reference] in the Irurueta Docs site, which explains the protocol itself; these pages
explain how this example implements it.

A *use case* here is a protocol flow, not one of the `*UseCase` classes of the `application` modules: one flow
usually runs several of them.

== Which flow for which client

[mermaid]
....
flowchart TD
  Start(["Who needs a token?"]) --> User{"Is a user present?"}
  User -- "yes" --> Browser{"Does the client run in a browser?"}
  Browser -- "yes, behind a backend" --> BFF["Authorization code + PKCE through the BFF"]
  Browser -- "yes, JavaScript only" --> SPA["Authorization code + PKCE, public client"]
  Browser -- "no keyboard or browser" --> Device["Device authorization grant"]
  User -- "no, a service" --> Own{"Acting for itself?"}
  Own -- "yes" --> CC["Client credentials"]
  Own -- "no, on behalf of a user" --> TE["Token exchange"]
....

The password, passkey, one-time code, social and certificate sign-ins are not OAuth grants: they are how the user
authenticates inside the authorization code flow, between the authorization request and the code being issued, and
are described together in xref:use-cases/authentication-methods.adoc[]. The feature pages (for example
xref:mfa-and-step-up.adoc[] or xref:x509.adoc[]) describe how each piece is built.
