= OpenID Connect sign-in

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

OpenID Connect adds an identity layer to the authorization code flow: a client that asks for the `openid` scope gets an
ID token that tells it who signed in, how and when, and may call the UserInfo endpoint for profile claims. `auth-server`
enables OpenID Connect on its protocol chain (`server.oidc(...)` in `SecurityConfig.authorizationServerSecurityFilterChain`),
publishes its metadata at the OpenID Connect discovery and RFC 8414 endpoints, and signs every token with RSA keys that
are persisted in PostgreSQL and rotated, publishing the public halves at the JWKS endpoint. Custom claims (`roles`,
`tenant`, `aud`, `amr`, `acr`, `auth_time`, `idp`) are added by `IssuedTokenClaims` and the `JwtClaimsContributor` beans.

== At a glance

[cols="1,3",options="header"]
|===
|Item
|Value

|Actors
|User and browser, a relying party (in this repository the `bff`, through Spring Security's `oauth2Login`),
`auth-server`.

|Clients
|Any client with the `openid` scope: the seeded `bff` and `spa-public` both have it. The device grant's `device-client`
has none (Spring Authorization Server refuses `openid` in device requests).

|Preconditions
|The issuer is `spring.security.oauth2.authorizationserver.issuer` (`AUTHSERVER_ISSUER_URL`, default
`http://localhost:9000`). Signing keys need the key-encryption secret (`authserver.keys.encryption.password` and
`.salt`, generated per machine by `DevKeyEncryptionSecret` under the `dev` profile). Nothing else to enable.

|Endpoints
|`GET /.well-known/openid-configuration` (OpenID Connect Discovery), `GET /.well-known/oauth-authorization-server`
(RFC 8414), `GET /oauth2/jwks`, `GET /oauth2/authorize`, `POST /oauth2/token`, `GET` or `POST /userinfo`,
`/connect/logout` (see xref:use-cases/logout.adoc[]) and, when enabled, `/connect/register` (see
xref:use-cases/dynamic-client-registration.adoc[]).
|===

== Steps

. The relying party reads `/.well-known/openid-configuration` (public, no session needed). It names the `issuer`, the
authorization, token, JWKS, UserInfo and end-session endpoints, the supported scopes, response types, client
authentication methods and signing algorithms. Feature customizers add to it, for example
`ClientAuthProtocolChainCustomizer` adds `mtls_endpoint_aliases` when `authserver.x509.port` is set, and
`registration_endpoint` appears only with dynamic registration enabled.
. It redirects the browser to `/oauth2/authorize` with `response_type=code`, `scope=openid ...`, `state`, `nonce` and a
PKCE challenge (see xref:use-cases/authorization-code-bff.adoc[]). It may add `acr_values` and `max_age`, which
`StepUpAuthorizationRequestConverter` reads (see xref:use-cases/step-up.adoc[]).
. The user signs in and, if needed, proves a second factor and consents. Each method grants a `FACTOR_*` authority,
which later becomes `amr` and `acr`.
. The relying party exchanges the code at `/oauth2/token` and receives an access token, a refresh token (confidential
clients) and an ID token.
. When Spring Authorization Server encodes each JWT, `RolesTenantAudienceTokenCustomizer` calls `IssuedTokenClaims`,
which adds `roles`, `tenant` and `aud` to access tokens only, then runs every `JwtClaimsContributor` on access and ID
tokens: `MfaClaimsContributor` (`amr`, `acr`, and `auth_time` on access tokens), `IdpClaimsContributor` (`idp` after a
social sign-in) and `TokenExchangeAudienceContributor` (exchanged tokens only). The `JwtEncoder` signs with the
`ACTIVE` key of `signing_keys`.
. The relying party fetches `/oauth2/jwks` and verifies the ID token signature, `iss`, `aud` (its client id), `exp` and
`nonce`. The key set (`DatabaseJwkSourceConfiguration`) contains the `ACTIVE` and `NEXT` keys and every `RETIRED` key
still within its effective retention, cached for `authserver.keys.jwks-cache-ttl` (default `PT30S`), so a token
signed before a rotation keeps validating.
. Optionally, it calls `/userinfo` with the access token as a bearer token. The framework checks the token and its
`openid` scope and `UserInfoMapper` (registered by `UserInfoConfiguration` through a `ProtocolChainCustomizer`) builds
the answer from the user's account, limited to the granted scopes.

== Tokens and claims

[cols="1,2,2",options="header"]
|===
|Claim
|ID token
|Access token (JWT)

|`iss`, `sub`, `iat`, `exp`, `jti`
|Yes; `sub` is the local username for every sign-in method; lifetime fixed by the framework at 30 minutes
|Yes; lifetime from the client (10 minutes for the seeded clients)

|`aud`
|The client id
|The client's `audiences` setting (`resource-server` and `auth-server` for the seeded clients), else the client id

|`azp`, `nonce`
|Set by the framework (`nonce` when the request sent one)
|No

|`sid`, `auth_time`
|Set by the framework from the session
|`auth_time` by `MfaClaimsContributor`: epoch second of the primary factor

|`scope`
|No
|The granted scopes

|`roles`, `tenant`
|No (they are in UserInfo with `profile`)
|Yes, for user grants; never for `client_credentials`

|`amr`
|RFC 8176 values of the factors presented (`pwd`, `otp`, `sms`, `hwk`, `fed`, ...), plus `mfa` for a multi-factor sign-in
|Same

|`acr`
|`urn:irurueta:acr:pwd` or `urn:irurueta:acr:mfa`
|Same

|`idp`
|After a social sign-in (`IdpClaimsContributor`)
|Same
|===

UserInfo answers `sub` always, `preferred_username`, `roles` and `tenant` with `profile`, `email` and
`email_verified` with `email`. The seeded clients do not have the `email` scope, so they get no e-mail claims.

== How it is tested

* `auth-server/boot` `AuthorizationCodePkceIT`: the access and ID tokens validate against `/oauth2/jwks`; the ID token's
`sub`, `aud`, `nonce` and `iss` are checked.
* `auth-server/boot` `SecurityIT` and `SecurityConfigIT`: `/.well-known/openid-configuration` and `/oauth2/jwks` are
public and the issuer is the configured one.
* `auth-server/boot` `TokenFlowIT`: access token claims (`aud`, `roles`, `tenant`, `scope`), UserInfo with `profile`
and `email`, and UserInfo refused without or with an invalid token.
* `auth-server/boot` `KeyRotationIT`: the key set in each state of the rotation lifecycle, and a token signed before a
rotation stays valid until its key is removed.
* `auth-server/boot` `StepUpIT`: `acr_values` and `max_age` on the authorization request.
* `auth-server/boot` `ParIT`: the discovery metadata advertises the PAR endpoint only when it is enabled.
* `e2e-tests` `PasskeyEndToEndIT`: `amr` reports `hwk` alone, or `pwd`, `hwk` and `mfa`.
