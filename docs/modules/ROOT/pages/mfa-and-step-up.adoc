= Multi-factor authentication and step-up

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

The password is the first factor. A second factor (a TOTP code or a recovery code) is asked when a request needs it,
and the tokens that come out of that sign-in say so, so a resource server can demand a recent multi-factor sign-in
for sensitive operations (RFC 9470).

== Second-factor page

A user who signed in with a password and whose request needs a second factor is sent to `GET /login/second-factor`.
The page is defined by the contract `apis/auth-server/web-pages/auth-server-pages-v1.yaml`;
`SecondFactorController` implements the generated interface and renders `second-factor.html`, which shows the form of
every `SecondFactorFragment` bean (see `LoginMethodFragment` in xref:login-and-bff.adoc[]). A factor is added by
declaring its own fragment and filter, never by editing the page.

=== Enrollment and account API

The user enrolls an authenticator and manages the recovery codes and trusted devices through the account API, defined
in `apis/auth-server/rest-server/auth-server-api-v1.yaml`.

[cols="2,3",options="header"]
|===
|Endpoint
|Behavior

|`POST /api/account/totp`
|Starts the enrollment: returns the secret, the `otpauth://` URI and a QR code.

|`POST /api/account/totp/confirm`
|Confirms the enrollment with a first code and returns the recovery codes (shown once).

|`DELETE /api/account/totp`
|Disables TOTP.

|`POST /api/account/recovery-codes`
|Generates a new set of recovery codes, invalidating the previous ones.

|`GET /api/account/trusted-devices`
|Lists the devices that skip the second factor.

|`DELETE /api/account/trusted-devices/\{id}`
|Revokes a trusted device.
|===

== Trusted devices and configuration

After a successful second factor the user may trust the device: a cookie lets later sign-ins skip the second factor
until `authserver.mfa.trusted-device-validity` elapses or the device is revoked.

[cols="2,1,3",options="header"]
|===
|Property (`authserver.mfa.*`)
|Default
|Meaning

|`max-failed-attempts`
|5
|Consecutive failed attempts that lock the second factor.

|`lockout`
|15 minutes
|How long the second factor stays locked.

|`trusted-device-validity`
|30 days
|How long a trusted device skips the second factor.

|`totp-issuer`
|`Irurueta Auth Server`
|Issuer shown by the authenticator app.
|===

== Step-up

A client asks for a recent multi-factor sign-in with the `acr_values` and `max_age` authorization request parameters.
The tokens then carry `amr`, `acr` (`urn:irurueta:acr:mfa`) and `auth_time` (`MfaClaimsContributor`), and the
resource server enforces the policy; see xref:resource-server.adoc[].
