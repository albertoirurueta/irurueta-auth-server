= Multi-factor authentication and step-up

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

The password is the first factor. A second factor (a TOTP code or a recovery code) is asked when a request needs it,
and the tokens that come out of that sign-in say so, so a resource server, or this server's own account API, can
demand a recent multi-factor sign-in for sensitive operations (RFC 9470).

== When a second factor is required

A second factor is required when the client asks for it (its `mfaRequired` setting, read through
`IsClientMfaRequiredUseCase` and the client port, so only the persistence adapter knows how it is stored), when an administrator forced it
on the account (`users.mfa_required`) or when the user has confirmed a second factor: a factor the user enrolled
protects every sign-in, whatever the client. The administrator flag stays separate, so removing the last second factor
lifts the requirement only when no administrator set it. "Has a confirmed second factor" asks every
`SecondFactorEnrolmentQuery` bean (TOTP's is `IsTotpEnabledUseCase`, and the passkeys' is `HasConfirmedPasskeyUseCase`, see xref:passkeys.adoc[]), so a later second factor joins by declaring its
own.

=== Lockout

Failed attempts are recorded through `SecondFactorAttemptRepository`; after `authserver.mfa.max-failed-attempts`
consecutive failures the second factor is locked for `authserver.mfa.lockout`. Every verification (TOTP code, recovery
code, enrolment code) starts with `CheckSecondFactorLockoutUseCase`, which reads the user's attempt row `FOR UPDATE`
inside the use case's transaction: concurrent attempts of the same user run one after the other, so none of them can
pass the check while another is about to count a failure.

== TOTP and recovery codes

The code is verified by `TotpAuthenticationFilter` (`POST /login/second-factor/totp`) through
`TotpAuthenticationProvider`; a recovery code is accepted in the same form and is consumed when used. Recovery codes
only stand in for a confirmed second factor: they are generated (`GenerateRecoveryCodesUseCase`) and accepted
(`VerifyRecoveryCodeUseCase`) only while the account has one, and an attempt without it fails and counts towards the
lockout. On success the
session id changes and the CSRF token is renewed, with the same session authentication strategy the form login uses
(`TotpChainCustomizer` hands the chain's shared strategy to the filter).

=== Enrolment during the sign-in

A user who must present a second factor but has none is not stuck: the TOTP fragment shows the enrolment form instead
(a new pending secret as a QR code and as its `otpauth` URI). The QR code is a `data:` URI, which the pages'
Content-Security-Policy allows for images. The first code is posted to the same filter with the `enroll` field;
`ConfirmTotpAtSignInUseCase` confirms the app (a wrong code counts towards the lockout) and the code is the second
factor of that sign-in. The browser then goes to `GET /login/second-factor/recovery-codes`, which shows the new
recovery codes once (they are taken out of the session as the page renders) and whose Continue link resumes the
interrupted authorization request.

=== Enrollment and account API

The user enrolls an authenticator and manages the recovery codes and trusted devices through the account API, defined
in `apis/auth-server/rest-server/auth-server-api-v1.yaml`.

[cols="2,3",options="header"]
|===
|Endpoint
|Behavior

|`POST /api/account/totp`
|Starts the enrollment: returns the secret, the `otpauth://` URI and a QR code.

|`POST /api/account/totp/confirm`
|Confirms the enrollment with a first code and returns the recovery codes (shown once).

|`DELETE /api/account/totp`
|Disables TOTP, removes the recovery codes and revokes every trusted device. Needs a step-up.

|`POST /api/account/recovery-codes`
|Generates a new set of recovery codes, invalidating the previous ones. Needs a confirmed authenticator app
(otherwise `400`, problem type `urn:problem:mfa:totp-not-enrolled`) and a step-up.

|`GET /api/account/trusted-devices`
|Lists the devices that skip the second factor.

|`DELETE /api/account/trusted-devices/\{id}`
|Revokes a trusted device. Needs a step-up.
|===

=== Step-up on the account API

Removing or resetting the second factor must not be possible with a stolen token or a session left open. While the
account has a confirmed second factor, `StepUpGuard` (called first by those controllers; the `/api/**` security chain is
unchanged) requires the bearer token to show a multi-factor sign-in (`acr` `urn:irurueta:acr:mfa`) whose `auth_time`
is within `authserver.mfa.step-up-max-age`. Otherwise the answer is `401` with
`WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="urn:irurueta:acr:mfa", max_age="300"`
and a problem body: the client signs the user in again with those `acr_values` and `max_age` and retries. An account
without a second factor cannot step up and is not asked to.

== Trusted devices and configuration

After a successful second factor the user may trust the device: a cookie lets later sign-ins skip the second factor
until `authserver.mfa.trusted-device-validity` elapses, the device is revoked or the second factor is disabled. The
cookie grants `FACTOR_TRUSTED_DEVICE`, a factor of strength `REMEMBERED`: it satisfies the sign-in policy, but it proves
nothing about this sign-in, so the tokens report the password only (`amr [pwd]`, `acr urn:irurueta:acr:pwd`) and a
step-up request (`acr_values` asking for the multi-factor class) still needs a real second factor. When the
second-factor page is reached for such a step-up, the trusted-device filter lets the page render the TOTP form instead
of resuming the request (which would only redirect back). Recognising a device changes the session id.

The cookie (`__Host-TRUSTED-DEVICE`, `HttpOnly`, `Secure`, `SameSite=Lax`) holds the random token signed with
HMAC-SHA256, as `<token>.<signature>` (Base64url). `TrustedDeviceTokenSigner` is a domain port;
`HmacTrustedDeviceTokenSigner` in `infrastructure/keys` implements it with a key derived from the key-encryption secret
for this purpose only (`PurposeKeyDerivation`, see <<purpose-keys>>). `FindTrustedDeviceUseCase` checks the signature,
in constant time, before the account or the device is looked up, so an unsigned or forged value is rejected at no
database cost; only the SHA-256 hash of the token is stored. The cookie is only evaluated on the second-factor page
(`GET /login/second-factor`), where every request that owes a second factor is sent: other requests are not looked
into, so a user who never gets the factor is not looked up on every request.

[[purpose-keys]]
=== Keys derived per purpose

The TOTP secrets are encrypted at rest (`AesGcmTotpSecretCipher`, AES-256-GCM) and the trusted-device cookie is signed,
both from the key-encryption secret (`authserver.keys.encryption.password` and `.salt`), but neither shares the key
that protects the signing keys. `PurposeKeyDerivation` derives a salt per purpose (HMAC-SHA256 of the purpose label,
`totp-secret` or `trusted-device-cookie`, keyed with the configured salt) and, for the cookie, a 256-bit key from the
passphrase and that salt (PBKDF2-HMAC-SHA256). The signing-key cipher (`AesGcmKeyCipher`) keeps the configured salt, so
the keys already stored still decrypt.

== Step-up

A client asks for a recent multi-factor sign-in with the `acr_values` and `max_age` authorization request parameters.
The tokens then carry `amr`, `acr` (`urn:irurueta:acr:mfa`) and `auth_time` (`MfaClaimsContributor`), and the
resource server enforces the policy; see xref:resource-server.adoc[]. Both the claims and the step-up checks read the
factors through `FactorTimeline`: a remembered device never counts, and `auth_time` (and so `max_age`) is the time of
the primary factor, not of a later second factor, so adding a code never makes an old sign-in look recent.
